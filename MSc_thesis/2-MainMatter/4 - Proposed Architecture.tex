\chapter{Implementation}
\label{cha:proposed-architecture}

This chapter documents how the testbed was actually built: the physical hardware, the network topology connecting it, and the software stack for both the Core and the two Radio Access Networks. Section~\ref{sec:system-overview} gives an overview of the overall system and how its four machines are laid out and connected. Section~\ref{sec:hardware-components} details the physical hardware assets, software-defined radios and clock synchronization equipment. Section~\ref{sec:core} describes the implementation of the Core Network, Section~\ref{sec:ran} outlines the structure of the Radio Access Network for both generations, and Section~\ref{sec:ue} describes the user equipment used to connect to the network. Section~\ref{sec:data-collection} lists the logs, packet captures and test outputs the testbed records, from which every result in this dissertation is drawn, and Section~\ref{sec:architecture-summary} brings the chapter together in a single diagram of the testbed. %CHANGED BY CLAUDE (roadmap: user equipment removed from hardware sentence, metrics and summary sections added)

\section{System Architecture Overview}
\label{sec:system-overview}

The testbed is built around four machines: one running the 5G \gls{RAN}, another running the 4G \gls{RAN}, a third running the Core network (shared by both generations), and a fourth reserved for a 5G \gls{NSA} deployment that was ultimately not implemented. Each working \gls{RAN} is kept on its own dedicated machine rather than sharing a single host between radio access technologies, so that the 4G and 5G networks can run independently of one another rather than being intermingled on the same machine. This choice simplifies the management of each network and follows directly from one of the goals of this dissertation: to leave a working network testbed in place, rather than a single disposable experiment, for future projects to build on and explore. It makes the testbed easier to navigate for the students and researchers who continue this work. The software, configuration files and attached radio for one generation's \gls{RAN} are all found on that generation's machine, and the Core network for both generations is found on the Core machine. Someone interested in only one generation can therefore start from a single machine, without having to separate its components from those of the other.

The machines connect to each other through an Ethernet switch, with static IP addresses assigned to each one, as shown in Figure~\ref{fig:ip-addresses}.

For the radio, two \glspl{SDR} were chosen:
\begin{itemize}
    \item \underline {National Instruments B210}: This is a mid-level \gls{SDR} that uses UHD, the gold standard for \gls{SDR} development. These boards are widely used in research projects and testbeds, and they are natively compatible with most \gls{SDR} software.
    \item \underline {Nuand bladeRF xA4}: This is a cheaper mid-level \gls{SDR} that uses a proprietary library, libbladeRF, for communication with the host machine. It is less used than the USRP B210 in research projects, as it is not directly compatible with most software. Through the use of a wrapper library, it is possible to use this \gls{SDR} with most software which does not natively support it.
\end{itemize}

Both of these boards use an Analog Devices AD9361 transceiver, which makes their \glsxtrshort{RF} capabilities theoretically similar. The main difference between them is their \glspl{FPGA}, in which the B210 uses a Xilinx Spartan-6, while the bladeRF xA4 uses an Intel Altera Cyclone V.

Along with the \glspl{SDR}, a Leo Bodnar \gls{GPSDO} was chosen to provide a stable clock source for the NI B2901, which is crucial for the proper operation of the 5G network, given the strict timing requirements of the 5G standard, compounded by the TDD operation. The \gls{GPSDO} provides a stable 10 MHz reference clock and a 1PPS signal, which are used to synchronize the \gls{SDR} and ensure accurate timing for the transmission and reception of signals.

Connected to the 4G \gls{RAN} machine is the Nuand bladeRF xA4 (Figure~\ref{fig:bladerf}), which was used for the 4G deployment. This board, unlike the B2901, was powered entirely over its USB connection to the RAN machine, with no separate power supply used.

Connected to the 5G \gls{RAN} machine is an NI B2901 (Figure~\ref{fig:b2901-gpsdo}), the National Instruments designation for the USRP B210 described above. In addition to its USB connection to the RAN machine, the B2901 was connected to a wall socket through its own power supply, which was required to sustain the board at the gain settings used during testing. Along with the board, the Leo Bodnar GPSDO was connected to provide both a stable clock source and a 1PPS signal for synchronization. The GPSDO's GPS lock was verified using \texttt{lbgpsdo}~\cite{lbgpsdo}, an open-source command-line utility for configuring and querying Leo Bodnar GPSDO devices.

\section{Core}
\label{sec:core}

The core network is implemented using Open5GS~\cite{open5gs_repo}, an open-source project that provides both a complete 5G core network (5GC) and a 4G \gls{EPC} implementation, following the \gls{3GPP} Release 17 specifications. This dual support makes the 4G/5G comparison possible on shared hardware, as the same Open5GS deployment serves as the core for both generations, so the 4G baseline and the 5G network under test differ only in their \gls{RAN}. Open5GS is designed to be modular, with each network function implemented as a separate process, each with its own configuration file on the machine. Subscriber data for both generations is held in a single MongoDB database, which Open5GS uses as its backend. The core network is deployed on its own dedicated machine.

The Open5GS~\cite{open5gs_repo} core ran at version 2.8.0, with the main configuration values listed in Table~\ref{tab:core-config}. Harking back to the reusability objective stated in the Introduction, all configuration files for the core were made available in a GitHub repository~\cite{thesis_repo}, and a script to deploy them directly onto the core machine was created and made public, allowing anyone to redeploy the same core configuration without having to reconstruct it by hand. The script \texttt{deploy\_open5gs\_configs.sh} checks out the configuration files from the project's GitHub repository and deploys them directly onto the core host. This approach ensures that the testbed's configuration can be easily replicated in the future, supporting the goal of reusability and facilitating further research or experimentation based on this work.

Both generations are served by the same identity and addressing: a single PLMN, tracking area and data network, with every \gls{UE}, whether attached over 4G or 5G, drawing its IP address from the same pool. This is possible because Open5GS's \gls{SMF} and \gls{UPF} also act as the PGW-C and PGW-U of the \gls{EPC}, so the user plane of both generations terminates at the same function on the core machine. All interfaces facing the \glspl{RAN} are bound to the core machine's address, 10.0.0.10: the \gls{NGAP} (N2) and GTP-U (N3) endpoints for the 5G \gls{RAN}, and the \gls{MME} (S1-MME) and SGW-U (S1-U) endpoints for the 4G \gls{RAN}.

\section{\gls{RAN}}
\label{sec:ran}

The \gls{RAN} is implemented using srsRAN~\cite{ocudu_project} (renamed OCUDU partway through this project; see Section~\ref{sec:srsran}), an open-source software suite that provides a complete 5G \gls{NR} \gls{RAN}, following the \gls{3GPP} Release 17 specifications. Written in C++, it is modular by design, allowing the developer to customize both the \gls{CU} and \gls{DU} components of the \gls{gNB} separately. Each generation's \gls{RAN}, deployed on its dedicated machine, connects to its \gls{SDR} via USB 3.0.

\section{\glspl{UE}}
\label{sec:ue}

The proposed \gls{UE} for the testbed was a Motorola Moto G56 5G, a mid-range smartphone chosen for its 5G and eSIM support. This did not end up matching what was actually used: the Moto G56 struggled to connect to the network during testing, for a cause that was never identified and no speculation is made here. A Samsung Galaxy Z Flip5 (personal device) was brought in instead, and became the primary \gls{UE} for the actual test campaigns. Both devices connect to the network using an eSIM profile, provisioned through a remote SIM provisioning service. Table~\ref{tab:ue-comparison} compares the two candidate devices.

\section{Metrics Collection}
\label{sec:data-collection}

Every result presented in Chapter~\ref{cha:results} is drawn from records the testbed itself produces while running, rather than from external measurement equipment. Table~\ref{tab:data-sources} lists these sources.

The 5G \gls{RAN} is the more heavily measured of the two, because it was the network under investigation. In Round 1 its metrics were available only from the console, and its log also carried hex dumps of every message. From Round 2 onward the \gls{gNB} was configured to print its metrics into \texttt{gnb.log} with timestamps, which allows them to be aligned with the rest of the log, and hex dumps were turned off. %CHANGED BY CLAUDE (log volume figures recomputed from the gnb.log files of all three rounds)
In Round 1 the hex dumps made up 57 to 77\% of the lines in each log, or 41 to 60\% of its size, and the \gls{gNB} wrote an average of 1.7\,MB/s during testing, about 6.1\,GB per hour, with peaks of up to 12.9\,MB/s during saturated downlink tests. From Round 2 onward, without hex dumps but with the timestamped metrics and heavier traffic, the average fell to between 1.1 and 1.3\,MB/s, about 4 to 4.5\,GB per hour, and the peaks to 4.4\,MB/s. Anyone running the testbed continuously should plan for this, or lower the log levels.

\section{Summary}
\label{sec:architecture-summary}

Figure~\ref{fig:testbed-architecture} maps the elements described in this chapter together into a single view of the testbed as it was used in the test campaigns, and how it is connected. Both \gls{RAN} machines reach the core over Ethernet, so the 4G and 5G networks share everything behind the \gls{RAN} and differ in what lies in front of it: band, duplexing, bandwidth, \gls{SDR} and RF front-end, as listed in Table~\ref{tab:ran-config}.

This setup is the starting point for the evaluation that follows. Chapter~\ref{cha:methodology} describes how it was put to the test: where the \gls{UE} was placed relative to the radios, the traffic used to load each network, and the three test rounds across which the 5G \gls{RAN} configuration was adjusted, namely its TDD structure and \texttt{rx\_gain}, while the 4G network was left untouched as the baseline.
